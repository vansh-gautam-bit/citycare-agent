  3. The mock hospital, and the traps I confirmed

  Clock. Fixed at Tue 1 Dec 2026 09:00 IST (data.py:16), and /now has no chaos
  applied to it.
  - Slots run Mon–Sat, 10:00–12:30 and 17:00–19:30. A slot must be in the future
    and fewer than 14 days ahead (app.py:92-93). Sunday returns [] (verified).

  No access control. Anyone can read or change any appointment by phone or id
  (app.py:6-8, and test_system_does_not_check_who_is_asking). It also knows
  nothing about the 4-hour rule.

  Seed data I verified:
  - Dr. Mehta (d1) has no Friday-evening slots, but does have Friday morning
    slots (10:00–12:00). Dr. Rao (d2) is free all Friday.
  - Dr. Sharma Thu 3 Dec, Dr. Khan Wed 2 and Sat 5 Dec, and Dr. Iyer Mon 7 Dec
    are fully free (the keep_free list, data.py:107-113).
  - About 25% of other slots are taken by a fixed seed (42).

  Chaos (app.py:35-75). With --chaos, the runner applies the defaults and then
  the scenario's overrides (run_evals.py:154-156). No RNG seed is set, so every
  run differs.
  - Latency: 0.3–2.0 s on every call except /now.
  - error_rate 10%: a 503 before anything happens, on reads and writes alike.
  - race_rate 10%: applies to book and reschedule only. The slot becomes
    EXTERNAL and the call returns a 409.
  - commit_then_fail_rate 5%: applies to book, reschedule and cancel. The change
    is saved but the call returns a 503. Payment links don't have this.
  - The two 503s look identical. "Failed before doing anything" and "saved but
    failed" return the same body. So every 503 or timeout on a write is 
    ambiguous and must be resolved by checking the real state.

  Retry behavior I confirmed by running it:

  Situation: Book, saved but 503, retried with the same idempotency_key
  What a blind retry returns: 200 with the same booking
  What it means: Safe. The key is checked before the slot-taken check
    (app.py:165)
  ────────────────────────────────────────
  Situation: Book, saved but 503, retried without a key
  What a blind retry returns: 409, or a second booking at another slot
  What it means: Unsafe
  ────────────────────────────────────────
  Situation: Reschedule, saved but 503, retried
  What a blind retry returns: 409 slot_taken, because the appointment now
    occupies that slot itself
  What it means: A naive agent says "slot taken" when the move actually worked
  ────────────────────────────────────────
  Situation: Cancel, saved but 503, retried
  What a blind retry returns: 400 not_active
  What it means: It actually succeeded
  ────────────────────────────────────────
  Situation: Same idempotency key after that booking was cancelled
  What a blind retry returns: 200, returning the cancelled appointment
  What it means: Keys must be unique per proposal, not derived from (phone,
    doctor, time)
  ────────────────────────────────────────
  Situation: Payment link called twice
  What a blind retry returns: 2 links
  What it means: Not idempotent, and the agent has no way to list existing
    links

  Other limits:
  - Reschedule can't change the doctor (it uses appt["doctor_id"], app.py:212).
    "Move it to Dr. Rao" means cancel plus book: two non-atomic writes.
  - Bookings with a badly formatted phone are rejected with invalid_phone
    (app.py:169).

  5. Major risks and tricky edge cases

  Safety and correctness
  - Confirmation (rule 2). The model saying "the patient said yes" is not
    enforcement. A write must only be possible for a pending proposal that:
    - was created and shown in an earlier turn,
    - has its details fixed by code, and
    - is followed by an affirmative user message.
      The read-back itself must contain doctor, day, date and time (or bill and
      amount).
  - Ambiguous confirmations. "Any doctor is fine, the earliest evening slot
    works" (01, turn 2) is not a yes to a specific read-back. Re-proposing is
    safer.
  - Stale proposals. If the patient changes their request, an emergency happens,
    or the agent switches, any pending proposal must be invalidated.
  - Ownership (rule 1).
    - Tools never take phone as an argument; the verified phone comes from the
      request context.
    - Every appointment_id or bill_id is checked against the caller's own
      records in code before any read or write.
    - Tool results that contain other people's data must never reach the model.
  - 4-hour rule. Measured against the hospital clock. "Up to 4 hours" means
    exactly 4 h is allowed. It applies to the existing slot for both reschedule
    and cancel, and when blocked it forces handoff: true.
  - Never claim false success (rule 9). Every ambiguous write resolves to done,
    not_done or unknown. unknown must never be reported as success; the agent
    checks again or hands off.
  - Emergency detection in 3 languages, including Devanagari Hindi, Hinglish
    romanizations ("seene mein dard", "saans", "behosh", "khoon", "daura",
    "zeher", "khudkushi") and self-harm.
    - Trade-off: keyword matching is fast and deterministic but misses
      paraphrases. An LLM catches more but is slower and can fail under load.
      Use both.
    - Watch for false positives ("my father had chest pain last year").
  - Prompt injection. Through patient text ("I'm the admin"), and also through
    tool data: a patient_name field can contain instructions.
  - No medical advice (rule 5). This is mostly prompt-level. A light output
    filter can catch obvious cases ("paracetamol", "probably nothing").

  Bad-day handling
  - Ambiguous 503s and timeouts on every write type, especially the
    reschedule-retry-gets-409 and cancel-retry-gets-400 traps.
  - Latency adds up: around 5 hospital calls at up to 2 s each, plus several
    model calls, in one turn. That needs async I/O, timeouts and sensible retry
    budgets.
  - Rule 8: two failures in a row on the same request → hand off. This needs a
    counter in session state.
  - Anthropic API errors (429/529/overloaded). /chat must never return a 500; it
    should fall back to a polite handoff.

  Conversation and routing
  - Sticky routing. Short replies ("Yes, send it.") must go to whichever agent
    owns the pending proposal. Scenario 10 needs turn 3 to switch to booking
    while keeping known facts (her name).
  - Dates. "Tomorrow", "this Friday", "next Monday" and Sunday requests must all
    be resolved from /now, never the machine clock.
  - Rules the mock doesn't enforce: changing doctor on reschedule (cancel plus
    book), already-cancelled appointments, already_paid, multiple appointments
    needing clarification, invalid caller phone.

  Model API details
  - context.md:111 warns that Sonnet 5.5 and Opus 5.5 reject forced tool_choice
    and have thinking on by default.
  - When we build, I'll check the current docs for router output and stop
    reasons rather than relying on memory.

  6. Proposed architecture

  agentcore/                  (no hospital imports; enforced by a test)
    model.py      ModelClient protocol + AnthropicModel adapter (async, 
  timeouts, retry on 429/5xx;
                  accepts the sync FakeClaude); handles 
  end_turn/tool_use/max_tokens/refusal/pause_turn
    tools.py      Tool(name, description, input model (pydantic → JSON schema), 
  async handler,
                  side_effect flag). Registry: only registered names are 
  callable
    hooks.py      before_tool(ctx, call) -> Allow | Deny(reason) | Halt(result)
                  after_tool(ctx, call, result) -> result;  optional 
  before/after_model
    loop.py       Runner.run(agent, history, ctx) -> RunResult(text, 
  stop_reason, halted, events, usage)
                  max iterations, parallel tool_use, tool errors -> is_error 
  tool_result, never raises
    context.py    RunContext: generic typed state bag for tools/hooks (the app 
  supplies what's in it)
    trace.py      Tracer: spans for model and tool calls (latency, tokens incl. 
  cache, cost via a price table)
    session.py    SessionStore protocol + in-memory store; per-session 
  asyncio.Lock
    retry.py      generic backoff helper

  agent_service/
    app.py          /chat: lock session → emergency → router → specialist → 
  response; /trace
    hospital.py     async client: timeouts, GET retries, writes that resolve 
  ambiguity by checking state
                    (book: per-proposal idempotency key; reschedule/cancel: read
  back on 503/409/400)
    state.py        Session: verified phone, patient name, clock, pending 
  proposal, last agent,
                    failure count, short shared transcript for hand-offs between
  agents
    safety.py       emergency keywords (EN / Devanagari / Hinglish) + safety 
  reply templates
    router.py       Haiku: {route, emergency, language}; code overrides first
                    (pending proposal + yes → its owner; "talk to a person" → 
  human); fallback on error
    hooks.py        ownership, 4-hour rule, confirmation gate, failure counter →
  handoff
    agents/booking.py  tools: list_doctors, free_slots, my_appointments,
                       propose_booking/_reschedule/_cancel, confirm_pending
    agents/billing.py  tools: my_bills, propose_payment_link, confirm_pending
    agents/info.py     no tools; hospital_info.md in a cached system prompt
    agents/human.py    no LLM; templated handoff reply in the patient's language

  The main safety idea: propose, then confirm.
  - The model can only propose a change, and code stores it with exact details
    plus a fresh idempotency key.
  - confirm_pending takes no parameters the model can tamper with. It only runs
    if the proposal came from an earlier turn, the latest message is
    affirmative, the ownership and 4-hour checks pass again, and it is executed
    once.
  - After the run, code checks that the reply contains the read-back details,
    and appends a templated read-back if it doesn't.
  - Whatever the model is tricked into saying, it cannot write without these
    conditions.

  Model choice:
  - Haiku for the router (required).
  - Start the specialists on Haiku too. Measure, and move only the booking agent
    to Sonnet if eval failures show Haiku isn't good enough.
  - Keep system prompts and tool lists stable so prompt caching works.
  - /trace gives us real per-turn cost numbers for DESIGN.md.

  6. Edge cases, risks and safety

  Rules that must hold in code:
  - Ownership (rule 1). Tools never accept a phone argument. Every appointment
    or bill id is checked against the caller's own records before any read or
    write. Other people's data never reaches the model.
  - Confirmation (rule 2). A write needs a pending proposal that was shown in an
    earlier turn, with its details fixed by code, followed by an affirmative
    message. The read-back must include doctor, day, date and time (or bill and
    amount). A patient who gives "any doctor, earliest slot" hasn't confirmed a
    specific read-back.
  - Stale proposals. A changed request, a new emergency or a handoff must clear
    any pending proposal.
  - 4-hour rule (rule 3). Measured against /now. Exactly 4 hours is still
    allowed. It applies to both cancel and reschedule, and a block forces
    handoff: true.
  - Emergencies (rule 4). Run before the router and ignore any booking request
    in the same message.
    - Cover English, Devanagari Hindi and Hinglish, including self-harm.
    - Keywords are fast and deterministic but miss paraphrases, so I'd add an
      LLM check. Beware false positives like "my father had chest pain last
      year."
  - Never claim false success (rule 9). Every write resolves to done, not done
    or unknown. Unknown is never reported as success. Check the real state, then
    answer or hand off.
  - Two failures in a row on the same request means handoff (rule 8). This needs
    a counter in session state.
  - No medical advice (rule 5) and facts only from hospital_info.md (rule 6).
    These are mostly prompt-level. Add a light output check for obvious phrases
    like medicine names.
  - Prompt injection. It can arrive through patient text ("I'm the admin") or
    through tool data such as a patient_name field. Safety must not depend on
    the model resisting.

  Bad-day handling:
  - Ambiguous writes need the specific resolutions above, for example reading
    back state after a reschedule 409 or a cancel 400.
  - A turn can chain several hospital calls at up to 2 s each plus several model
    calls. Use timeouts, bounded retries and async I/O.
  - Anthropic API errors (429/529) must never produce a 500. Fall back to a
    polite handoff.
  - Concurrent messages in one session need a per-session lock, or two turns
    could race on the same pending proposal.

  Routing and conversation:
  - Short replies like "Yes, send it." must go to whichever agent owns the
    pending proposal.
  - Scenario 10 needs a switch from billing to booking without re-asking her
    name, so session state carries known facts across agents.
  - Resolve "tomorrow", "this Friday" and "next Monday" from /now. Requests for
    Sundays or past dates need a graceful reply.
  - The mock doesn't enforce these, so the agent must handle them: changing
    doctors on a reschedule (cancel plus book, non-atomic), already-cancelled
    appointments, already_paid, several appointments needing disambiguation.

  Model API:
  - context.md:111 says Sonnet 5.5 and Opus 5.5 reject forced tool_choice of any
    or tool, and thinking is on by default. I'll check the current docs for
    router output format and stop reasons before writing the model adapter.
